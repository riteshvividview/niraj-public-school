4. Should you change the region? YES — to Mumbai (ap-south-1)

Why

Facts
The project is in Tokyo (ap-northeast-1); the school, parents and staff are in India. A typical screen runs 3–8 database queries one after another.
Cost
India ↔ Tokyo is roughly 120–160 ms per query against 15–30 ms to Mumbai. Six queries waste about 0.8 s on distance alone — most of the "slow" 300–500 ms statements are this, not heavy SQL.
Rule
Database and app server in the same region, near the users: Supabase Mumbai + Vercel functions in Mumbai (bom1).
When
Now is the cheapest moment: 16 MB, no live traffic, no uploaded files in Storage.

How the move works (a region cannot be edited in place)

  1. Create a new Supabase project in South Asia (Mumbai).
  2. Apply our supabase/migrations/*.sql (npm run supabase:push), including today's hardening migration.
  3. Copy the data across and verify row counts table by table.
  4. Switch DATABASE_URI (pooler string) and keys, test everything, pause the Tokyo project (keep as a backup for a week).
A new project means new keys and a second billed project until the old one is paused. About an hour of work; no change visible to users.
